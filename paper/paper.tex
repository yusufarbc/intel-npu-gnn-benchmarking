\begin{abstract}
Neural processing units (NPUs) in client systems-on-chip (SoCs) target low-power inference, but their behavior on sparse graph neural networks (GNNs) remains underexplored. We characterize 14 GNN, CNN, and transformer models across the CPU, integrated GPU (iGPU), and NPU of an Intel Core Ultra platform using OpenVINO 2024.1. GNN experiments use fixed-shape graph inputs derived from three Open Graph Benchmark datasets. The NPU provides substantial CPU-relative speedups for selected dense FP32 models, including MobileNetV2 (4.5$\times$), ResNet-50 (8.0$\times$), and ViT-Tiny (11.4$\times$), whereas it provides little benefit over the CPU for most evaluated GNNs and the iGPU achieves the lowest latency for most GNN configurations. INT8 behavior is model-dependent: several models show marginal gains, SGC regresses by 2.2$\times$, and three architectures yield no executable INT8 configuration. Package-level measurements for selected CPU and iGPU configurations fall within 9--12.5\,W; direct NPU power isolation is unavailable. These results show that backend selection depends strongly on model structure, quantization compatibility, and verified device assignment. The suite is available at \url{https://yusufarbc.github.io/intel-npu-gnn-benchmarking/}.
\end{abstract}

\section{Introduction}

Neural processing units (NPUs) in client systems-on-chip (SoCs) are specialized hardware accelerators engineered for low-power, energy-efficient deep learning inference. In the Intel Meteor Lake processor architecture (e.g., Core Ultra 5 125H), the AI Boost NPU operates as a dedicated low-power engine alongside the multi-core CPU and integrated GPU (iGPU) within a nominal 28\,W mobile client form factor. While such consumer-tier client SoCs are optimized for computer vision workloads, their practical performance on sparse, irregular graph neural networks (GNNs) remains underexplored relative to high-power datacenter accelerators.

Unlike dense tensor operations, GNN execution combines sparse-times-dense matrix multiplication (SpDMM), often called SpMM in the GNN literature, with dynamic feature gathering over irregular adjacency structures, yielding high sensitivity to data movement \cite{9161360, 9218751}. As shown in Fig.~\ref{fig:fig3}, the exported GNN graphs contain 2--4$\times$ more shape-manipulation operators (Gather, Scatter, Reshape) than the vision graphs. These operators involve irregular index dependencies that are less regular than the dense tensor workloads targeted by the NPU's streaming-dataflow architecture. While prior works evaluate GNNs on server GPUs and custom ASICs \cite{9065592, 9858684, 10411398}, consumer client NPUs present a different design point: a restricted power envelope, shared system memory, compiler-managed data movement, and incomplete support for sparse or dynamic primitives \cite{intel_meteorlake_hotchips_2022, intel_core_ultra_npu}.

We develop a reproducible benchmarking suite evaluating 14 models across three Open Graph Benchmark (OGB) datasets and three Meteor Lake backends (CPU, iGPU, NPU) under OpenVINO 2024.1. The contribution is a boundary characterization of an accessible client NPU: it identifies where nominal accelerator availability translates into native execution, where quantization regresses, and where toolchain fallback can invalidate device-level comparisons. Our contributions include:

\begin{itemize}
    \item A reproducible profiling protocol (100 iterations $\times$ 3 runs $\times$ 3 datasets) extracting latency, throughput, precision gain, compilation outcomes, and ONNX Runtime execution traces.
    \item Cross-architectural latency comparisons showing that the iGPU achieves the lowest latency for most evaluated GNNs, whereas the NPU provides its largest CPU-relative gains on selected dense FP32 models.
    \item Empirical evidence showing INT8 quantization provides minimal or negative returns on the NPU for GNNs, with two attention-based architectures yielding no executable INT8 configuration.
    \item Analysis of operator composition, execution anomalies, and graph-size scaling under static-shape NPU compilation on a client platform.
\end{itemize}

\section{Background}

\subsection{GNN Computation and Acceleration Landscape}
Graph neural network architectures compute node representations via iterative neighborhood aggregation. Across spectral \cite{kipf2017gcn, pmlr-v97-wu19e}, spatial \cite{10.5555/3294771.3294869, xu2018how}, attentional \cite{velickovic2018graph, brody2022how, shi2020masked}, and propagation-based \cite{gasteiger2019appnp, pmlr-v70-gilmer17a} models, a central computational primitive is sparse-times-dense matrix multiplication (SpDMM), combined with nonlinear feature transformations. These operations exhibit irregular memory access patterns and poor spatial locality, stressing memory bandwidth and on-chip caches \cite{9161360, 9218751, 10.1145/3477141}.

To alleviate these memory bottlenecks, domain-specific GNN accelerators such as HyGCN \cite{9065592}, EnGN \cite{9161360}, GRIP \cite{9858684}, and TT-GNN \cite{10411398} implement dedicated hardware units for irregular edge gathering, custom scratchpad hierarchies, and crossbar interconnects. However, these custom ASICs require specialized non-commodity silicon. In contrast, commodity edge accelerators and client NPUs \cite{9926331, SINGH202371} are designed around dense matrix multiplication engines optimized for regular systolic dataflows.

\subsection{Intel Meteor Lake NPU Architecture}
Intel Meteor Lake client SoCs integrate the AI Boost NPU on the SoC tile and share system memory with the CPU and iGPU across the SoC fabric \cite{intel_meteorlake_hotchips_2022, intel_core_ultra_npu}. This client architecture makes end-to-end performance sensitive to data movement. Its streaming execution model favors continuous, predictable memory layouts (e.g., CNNs) but can incur overhead on irregular graph topologies with low data reuse. OpenVINO 2024.1.0 introduced a preview NPU plugin for Intel Core Ultra processors \cite{openvino_npu_docs}. In the evaluated ONNX Runtime/OpenVINO path, unsupported operations may remain on the host CPU. Requested-device labels and registered-provider lists alone do not establish per-operator placement, so we distinguish confirmed compilation outcomes from timing-based execution anomalies.

\subsection{Quantization and Edge Benchmarking}
Low-precision integer quantization (INT8) is standard practice for accelerating edge inference \cite{jacob2018quantization}. However, quantizing GNNs is complicated by high dynamic activation ranges and non-uniform degree distributions across graph nodes \cite{tailor2021degreequant}. Modern graph compilers apply operator fusion to minimize memory traffic \cite{10.1145/3453483.3454083, 11181270}, but sparse indexing patterns frequently break fusion chains. MLPerf Inference covers inference systems, while GNNMark characterizes GNN training on GPUs \cite{mlperf_inference, 9408205}; neither benchmark targets GNN inference on a Meteor Lake-class client NPU. Empirical evaluation with real-world graph datasets \cite{hu2020open} therefore remains an open area of research.

\section{Methodology}

\subsection{Experimental Platform}
Experiments were conducted on an Intel Core Ultra 5 125H mobile processor (nominal 28\,W processor base power, up to 4.50\,GHz maximum turbo frequency, 16\,GB LPDDR5x RAM, Windows 11 Build 26200) \cite{intel_core_ultra_125h_specs}. This is a power-constrained client platform rather than a server- or datacenter-class accelerator. The evaluated backends are: (1) the 14-core CPU (4 Performance, 8 Efficient, and 2 Low-Power Efficient cores), (2) the integrated Arc GPU (iGPU, Xe-LPG architecture, 7 Xe-cores), and (3) the AI Boost NPU (3720 series, VPUX37XX microarchitecture). OpenVINO's device identifier \texttt{GPU} refers to this integrated GPU; we use \emph{iGPU} throughout the paper. The software stack uses OpenVINO 2024.1 and ONNX Runtime 1.18.

Table~\ref{tab:models} lists the 14 evaluated models. \subsection{Datasets}
We use three real-world Open Graph Benchmark (OGB) datasets \cite{hu2020open} as graph-data sources (Table~\ref{tab:datasets}). For compatibility with the statically exported ONNX graphs, each GNN inference uses a fixed input containing 2,708 nodes, 10,000 edges, and 1,433 feature columns. Larger graphs are sampled, while edge lists and feature dimensions are truncated or zero-padded to the exported tensor shapes. Table~\ref{tab:datasets} therefore describes the source graphs rather than the effective density of the inference tensors, and the measurements do not represent full-graph OGB inference. Vision and NLP models receive synthetic inputs matching native shapes (e.g., $1\times3\times224\times224$ for CNNs); their repeated dataset labels use the same synthetic input and are not independent dataset workloads. Dataset preprocessing and tensor extraction run once in a separate Python subprocess before model warm-up and timing because the dataset and inference stacks require potentially conflicting native-library environments. The subprocess serializes the prepared tensors to disk and exits; process startup, loading, and serialization are excluded from the reported steady-state inference latency.

\subsection{Quantization Methodology}
The INT8 conversion pipeline is not uniform across model families. For GNNs, it first attempts NNCF post-training quantization with 300 synthetic samples matching the fixed export shapes and falls back to ONNX Runtime dynamic quantization if NNCF conversion fails. ResNet-50 and MobileNetV2 use NNCF with 50 synthetic image samples, whereas BERT-Tiny and locally exported additional baselines use ONNX Runtime dynamic quantization. The results therefore characterize the generated deployment artifacts rather than a controlled comparison of quantizers. FP32 and INT8 are the two evaluated precisions, not a claim about the complete set supported by the hardware. Post-quantization task accuracy was not evaluated, so Section~IV-B reports execution-performance outcomes rather than accuracy--performance trade-offs.

\subsection{Measurement Protocol}
Each configuration runs a 5-iteration warm-up and 100 timed iterations, repeated across three independent runs. We report the arithmetic mean and sample standard deviation of the three run means. Where confidence intervals are reported in the artifacts, they are two-sided Student-$t$ intervals over the three run means. All optimized runs use ONNX Runtime graph optimizations (\texttt{ORT\_ENABLE\_EXTENDED}) under the respective OpenVINO or CPU providers.

\subsection{Artifacts and Metrics}
We collect end-to-end inference latency ($T_{\text{inf}}$ in ms), throughput ($1000 / T_{\text{inf}}$ inferences/s), INT8/FP32 speedup ($T_{\text{FP32}} / T_{\text{INT8}}$), compilation status, runtime traces, and graph-optimization speedup ($T_{\text{baseline}} / T_{\text{optimized}}$). Package power is measured via Intel SoCWatch (\texttt{-f sys -t 30 -r sum}) for GCN and MPNN on CPU and iGPU backends; NPU-specific power-rail isolation was unsupported by the client platform telemetry.

\section{Results}

\subsection{Cross-Architectural Latency Comparison}
Inference latency is the mean wall-clock time in milliseconds ($T_{\text{inf}}$) for one batch-size-one forward pass after warm-up. It includes execution-provider dispatch and required host--device transfers, but excludes dataset loading, preprocessing, model conversion, and one-time graph compilation. For sequential batch-size-one execution, the corresponding throughput is $1000/T_{\text{inf}}$ inferences/s; latency is reported because it is the direct responsiveness metric for the targeted interactive edge setting. Fig.~\ref{fig:fig1} compares FP32 latencies across backends. The iGPU achieves the lowest latency for most GNNs, e.g., GraphTransformer (6.03\,ms iGPU vs. 10.72\,ms NPU vs. 10.69\,ms CPU) and APPNP (7.88\,ms iGPU vs. 11.75\,ms NPU vs. 11.82\,ms CPU). GCN reaches 6.94\,ms on iGPU and 7.91\,ms on NPU. Several GNNs show near parity between NPU and CPU, while GraphSAGE and SGC are exceptions to the broader iGPU-leading trend.
Conversely, the NPU provides substantial CPU-relative acceleration for selected dense workloads: MobileNetV2 achieves 1.90\,ms (4.5$\times$ over CPU), ResNet-50 runs at 3.94\,ms (8.0$\times$), and ViT-Tiny reaches 9.10\,ms (11.4$\times$ over CPU). The fastest backend remains model-dependent; the iGPU is faster than the NPU for EfficientNet-B0 and ViT-Tiny.

\subsection{INT8 Quantization: Performance Impact}
Table~\ref{tab:int8} shows INT8 speedups for available requested-NPU measurements. GraphTransformer improves by 1.21$\times$, while GCN, GIN, and GraphSAGE show marginal gains. Graph-node composition alone does not isolate the mechanism behind these differences. APPNP (0.84$\times$) and SGC regress; SGC's INT8 latency (173.90\,ms) is 2.2$\times$ slower than FP32 (78.59\,ms, 0.45$\times$ speedup). The experiment does not isolate a single compiler or runtime cause for this regression.
Device-assignment outcomes require cautious interpretation. MobileNetV2 INT8 on the requested NPU runs at 5.38\,ms versus 1.90\,ms in FP32 and is close to its 5.46\,ms CPU INT8 latency. This similarity is an execution anomaly, not conclusive evidence of CPU placement without a retained per-operator assignment trace. EfficientNet-B0 did not produce an executable INT8 configuration.

\subsection{Operator Composition Analysis}
Fig.~\ref{fig:fig3} reports the fraction of nodes in each exported ONNX graph; it is a structural composition, not an execution-time breakdown. Consequently, a large \textit{Other} segment does not imply that most latency is spent there. \textit{Other} groups inexpensive nonlinear activations (e.g., ReLU, GELU, Sigmoid), normalization, elementwise arithmetic (Add, Sub, Mul), and constant/slicing nodes that would otherwise make the legend unreadable. The relevant contrast is that GNN graphs contain 2--4$\times$ more Gather, Scatter, Reshape, and Concat nodes than vision graphs, whereas vision graphs contain a larger fraction of regular Conv nodes.
ViT-Tiny (5.7M parameters) achieves an 11.4$\times$ speedup, whereas GraphTransformer (0.18M parameters) shows no NPU speedup (10.72\,ms NPU vs. 10.69\,ms CPU). This contrast is consistent with their different operator structures, but graph composition alone does not isolate the cause of the latency difference.

\section{Discussion}

\subsection{Why INT8 Underperforms for GNNs on NPU}
The limited INT8 gains are consistent with the combination of irregular indexing, conversion/runtime overheads, and compiler coverage. Precision reduction lowers arithmetic cost but does not remove sparse Gather/Scatter traffic; the exported GNNs also contain 2--4$\times$ more shape-manipulation nodes than the vision models. Indirect indexing can restrict fusion opportunities \cite{10.1145/3453483.3454083}, although this experiment does not isolate individual compiler passes.

Outcomes are model-specific: MobileNetV2 INT8 exhibits CPU-like timing, no retained native-NPU result is available for MPNN, and three INT8 graphs fail to produce executable configurations. These exceptions make retained device-assignment evidence essential; timing similarity alone is not treated as proof of CPU placement.

\subsection{Platform Maturity Assessment}
Under OpenVINO 2024.1, the Meteor Lake NPU provides its largest CPU-relative gains for selected dense models (4.5--11.4$\times$), while the iGPU leads most evaluated GNN measurements. Graph-optimization ratios remain close to 1.0 on both iGPU and NPU. Memory-system behavior and compiler mapping are plausible contributors to the observed model dependence, but this benchmark does not isolate their effects.

\subsection{Comparison with Prior Work}
Custom GNN accelerators like HyGCN \cite{9065592} ($10^{3}\times$ over CPU), EnGN \cite{9161360} ($1.8\times10^{3}\times$ over CPU), and GRIP \cite{9858684} ($17\times$ over CPU) rely on hardware-native sparse engines and dedicated memory hierarchies. By contrast, the Meteor Lake NPU provides 0.9--1.2$\times$ acceleration for the evaluated GNNs over the CPU. These published speedups are not directly comparable because platforms, datasets, and baselines differ; they illustrate the distinct optimization targets of sparse GNN ASICs and commodity client NPUs. This distinction is consistent with observations in the wider edge AI landscape \cite{SINGH202371}.

\subsection{Limitations}

\textit{Single-Platform Scope:} All measurements were collected on a single Intel Core Ultra 5 125H processor (4P+8E+2LPE cores, 7 Xe-cores iGPU, one NPU tile). Results may vary across Meteor Lake configurations with different core/memory setups (LPDDR5x vs. DDR5) and subsequent architectures (Lunar Lake, Arrow Lake) due to differences in memory bandwidth.

\textit{Statistical Reporting:} Latencies represent arithmetic means over 100 iterations $\times$ 3 independent runs, with sample standard deviations and Student-$t$ intervals computed across the three run means. Formal paired hypothesis tests were not conducted. Small latency variations, such as the $\sim$6\% CPU--NPU gap for several GNNs, are not assessed for statistical significance, and rankings may be affected by run-to-run laptop environment variability (DVFS, thermal throttling).

\textit{Power Measurement Constraints:} SoCWatch measurements (Table~\ref{tab:energy}) cover only two models (GCN, MPNN) and two backends (CPU, iGPU). NPU power measurement was precluded by PMT hardware counter definitions, which expose NPU temperature and bandwidth (VPU\_MEMORY\_BW) but lack direct power rail counters, causing NPU-targeted sessions to produce only raw ETW files without power data.

\textit{Energy Estimation:} The latency-derived estimate ($\text{Avg Power} \times \text{Mean Latency}$) combines package power measured over a 30\,s collection window with separately measured steady-state latency. It does not isolate active inference energy from background activity, compilation, warm-up, or other workflow phases and should not be interpreted as a direct joule-per-inference measurement.

\textit{Compiler, Input, and Quantization Constraints:} The benchmark uses fixed 2,708-node, 10,000-edge inputs consistent with static-graph NPU compilation; it does not execute the complete OGB graphs. The mixed NNCF/ONNX Runtime conversion pipeline and absence of post-quantization task-accuracy evaluation limit controlled quantizer comparisons. Conversion provenance was not retained in the result tables, and no executable INT8 configuration was produced for GAT, GATv2, or EfficientNet-B0.

\textit{Workload Representativeness:} The selected GNN architectures include established models that remain common reference points for systems research, and the OGB datasets provide standardized, real-world graphs with widely varying size and density. Nevertheless, the suite does not cover newer large graph transformers, heterogeneous graphs, temporal graphs, or recommendation workloads. The results should therefore be interpreted as a characterization of representative foundational inference kernels on this client NPU, not as a comprehensive ranking of current GNN applications.

\textit{Software Stack Versioning:} Evaluation was limited to OpenVINO 2024.1 and ONNX Runtime 1.18. Since the OpenVINO NPU plugin is under active development, subsequent driver and software updates may expand operator coverage and improve GNN performance metrics.

\section{Conclusion}
Across 14 models and fixed-shape inputs derived from three OGB datasets, the Meteor Lake NPU provides 4.5--11.4$\times$ CPU-relative speedups for selected dense FP32 workloads but little latency benefit for most evaluated GNNs. INT8 outcomes include marginal gains, unavailable executable configurations, a CPU-like timing anomaly, and a 2.2$\times$ SGC regression; NPU power could not be isolated. The iGPU achieves the lowest latency for most tested GNNs, while the preferred backend for dense models remains model-dependent. These results motivate benchmarking each deployment artifact on its target backend and retaining device-assignment evidence for anomalous configurations. The suite is available at \url{https://yusufarbc.github.io/intel-npu-gnn-benchmarking/}.
